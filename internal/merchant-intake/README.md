# Merchant intake — internal readiness, not deployed
The institutional website contains disabled examples only. This isolated Node 22.16 SQLite reference has no HTTP endpoint, live binding, email provider or credentials. It is excluded from the website package. Tests use synthetic data and a temporary database.
Data flow: approved public intake -> server validation and verified consent -> atomic insert of request and outbox -> private reviewer queue -> notification containing reference only -> review decision with actor audit. Email delivery is not the source of truth. Approval of interest is not activation as a merchant.
Before real data: confirm responsible legal entity and approved privacy version, lawful basis and retention/deletion/rights procedure; approve private production storage and backups with restore tests; integrate server-side authentication (trusted identity, never take role from request), anti-abuse/rate limits, HTTPS, request idempotency and retry handling; configure verified recipient and email provider; implement outbox claiming/lease and delivery idempotency; run staging end-to-end synthetic tests including mail failure and duplicate/retry; approve launch separately. No secret, mailbox or real applicant data in Git. Never expose the reference implementation or SQLite file as a public asset.
The module implements persistence, duplicate-key handling, atomic outbox, review and explicit notification-result recording; role checks are only a service boundary, not a real authentication system. The production API, authenticated UI, mail worker, retention execution and cloud database remain unimplemented.
