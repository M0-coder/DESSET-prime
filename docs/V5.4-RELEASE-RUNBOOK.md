## 3. Preparación de cambio de web — diseño del procedimiento, NO ejecución

Solo cuando la matriz H01-H10 se cierre y el propietario apruebe la identidad, iniciar un **preflight en solo lectura**:

1. **Evidencia por SHA:** registrar PR, head SHA exacto, base SHA, logs CI y artefactos de Lighthouse/auditoría; confirmar que ninguno cambió después de la revisión.
2. Localizar la **revisión actual** de `M0-coder/DESSET`, la rama de despliegue que realmente utiliza Cloudflare y el deployment id SHA activo de `desset-institucional`. No suponer que los identificadores históricos siguen vigentes.
3. Comparar arquitectura: rutas, `_headers`, cache, assets, canonical/indexación, tratamiento `noindex`, links sociales, HTML responsive, flujos de descarga de apps solo cuando existan. El repositorio `DESSET-prime` no es automáticamente el repo de producción.
4. Guardar una **manifestación de rollback** antes de tocar nada: release branch, commit de origen validado, id de deploy Cloudflare, dominios y pruebas HTTP actuales. Tener copia inmutable y verificada del artefacto de producción previo.
5. Preparar revisión en entorno de **vista previa aislado**, sujeto a autorización separada, sin uso de `desset.lat` ni publicación de un proyecto sin `noindex` apropiado. El workflow actual no crea previews ni despliega.
6. Aprobar mediante decisión formal por SHA exacto, evidencias actualizadas y procedimiento de reversión ensayado; solo entonces redactar orden de implementación para la rama de release adecuada.

**Cualquier merge o despliegue requiere una autorización nueva y explícita.** No activar auto-merge ni publicar solo por pasar CI.

## 4. Plan de rollback en caso de cambio aprobado posteriormente

- **Trigger:** errores HTTP, assets rotos, pérdida de enlaces/SEO, falla de accesibilidad, degradación grave de rendimiento, permisos/cabeceras inseguros o contenido legal incorrecto.
- **Acción propuesta (NO ejecutada):** detener promoción, identificar último deployment id de Cloudflare comprobado y restaurar la versión anterior mediante procedimiento documentado y autorizado por el responsable. No tocar DNS por defecto.
- **Verificación:** HTTPS en `desset.lat` y `www.desset.lat`, status 200/404 esperado, CSP, HTML, scripts, logo, renderizados, enlaces, indexación según política aprobada, teléfonos y desktop. Medir diferencias y conservar logs.
- **Cierre:** registrar incidente, tiempos reales de recuperación (no inventar RTO), causa raíz, commits afectados, responsable, evidencia y siguiente autorización requerida.

- La versión es una **web institucional**, no un canal de pedidos, pagos ni contratación y no prueba actividad comercial.
- No hay evidencia ejecutada de testing en móviles físicos, lectores de pantalla humanos, derechos de marca ni seguridad avanzada; queda **NO-GO** para producción.
- Ni métricas de Lighthouse 100 ni esta acta equivalen a aceptación de diseño.
